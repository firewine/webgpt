[승인·후속 영향·실검증 한도](../reviews/r6-apparmor-impact-20261107.md), [SSOT](../development-plan.md), [설치·복구](../operations-runbook.md#r6-전용-apparmor-예외--명시-설치검사복구)를 따른다.

## 변경한 경계

| 대상 | 변경·유지 |
| --- | --- |
| `WorkspaceConfig/loadWorkspaceConfig` | optional `WJ_OUTER_BWRAP`, 검토된 절대 경로 하나만 허용. 미설정 시 기존 경로/동작 유지 |
| `ExecutionIsolation` / `outer-bwrap.ts` | 외부 실행기만 교체. root 소유·부모 쓰기/링크/ELF/stock 바이트/file capability/정책 파일/revision 검사, 실제 nested canary 필수. binary·정책 교체 시 proof 무효 |
| `CodexExecutor` / `RpcProcess` | 지정 모드의 읽기/쓰기 모두 외부 실행기 사용. 보호 실행의 동적 로더/Node/호출자 PATH 환경 제거, 내부 stock bwrap을 PATH 앞에 둠. 기본 RPC 호출자는 기존 allow-list 유지 |
| 설치/제거 도구 | 전용 root 소유 binary0750·정책0644만 생성, 패키지 checksum·stock enforce·override 없음 확인. 실패 시 만든 대상만 복귀. 살아 있는 전용 label/프로세스가 있으면 remove 거절 |
| 기존 backend | Store transaction/marker·권한 만료·job/capture/draft/explicit apply·보호 권한 ACCEPT 차단·예산·단일 실행·dot/Muse/Chrome 유지. 새 DB/API/로그인 경로 없음 |

의존성 주입의 기존 runtime→executor→isolation 경계를 유지하고 외부 실행기 identity만 작은 모듈로 분리했다. 새 실행 broker/보안 프레임워크/전역 서비스는 만들지 않았다. AppArmor revision fd는 첫 값 뒤 EOF를 기다리면 정지할 수 있어 한 번의 bounded read만 수행한다.

## 관측·검사

환경: Ubuntu26.04.1 LTS, Node24.18.0/npm11.16.0, CLI0.166.0, bwrap0.11.1, AppArmor parser5.0.2. 운영은 기존 `f648ea5`/4090의 정상 서비스이며 DB/방 off/Chrome 잠금/허용 roots `[]`를 변경하지 않았다.

| 항목 | 결과 |
| --- | --- |
| 변경 전 운영 권한 조건의 combined proof | SKIP/BLOCKED: `unpriv_bwrap`의 `sys_admin` 거절. 실제 커널 로그와 대조 |
| 전용 정책 구문 검사 | PASS, `--skip-kernel-load --skip-cache`만 수행. 로드/격리 성공으로 세지 않음 |
| 전체 `npm run check` | strict TypeScript/빌드, Node744건 중743 PASS/FAIL0/SKIP1. 기본 경로의 기존 결합 namespace 검사는 계속 차단되어 SKIP. 전용 경로는 아래 별도 PASS |
| 설치/제거 부정 검사 | 5 PASS. 실제 parser stdin 컴파일·링크·소유권/모드·checksum·stock capability deny/enforce·진행 중 프로세스·임의 경로/명령 거절 |
| 관련 Chromium 화면 | 보호 UI7건 PASS, 실행 업무 UI4건 PASS/0 SKIP. 빌드와 동시에 시작해 실행 파일1개를 읽지 못한 최초 실행은 실패로 남기고, 빌드 완료 후 그 파일4건을 재검사 |
| 설치 CLI 기존 요청 계약 | PASS, CLI0.166.0. 로그인/thread/model turn0 |
| 전용 정책 실제 설치 | PASS, 소유자가 sudo로 실행. binary root:firewine0750 / 정책 root:root0644. stock과 전용 binary SHA256 동일 `523da3e7399044be5163aee6f57a77a6bef7454376e28f0a0627920bae1b76b6` |
| 새 경로 combined proof | **1 PASS/0 SKIP**, `WJ_TEST_OUTER_BWRAP` 지정, `setpriv --no-new-privs` 조건. 실제 root/사본·비밀/네트워크·최종 label/capability 재획득 거절을 함께 확인 |
| 실제 Codex 읽기/쓰기/보고/반려/owner 검토 | NOT_RUN, 아래 선행 조건의 실제 무호출 대조 후 요청0 유지 |

기본 개발 도구 안의 실행은 호스트와 label/권한이 달라 검사 하위 프로세스 출력을 온전히 받지 못할 수 있다. 위 Node 검사 숫자는 호스트 조건에서 실제 subtest 결과를 받은 실행 기준이다. 개별 파일 프로세스 종료만 보고 하위 검사를 PASS로 올리지 않았다.

첫 설치는 parser에 stdin을 뜻하는 `-`를 넘겼지만 설치된 parser가 파일명으로 취급해 실패했다. root 파일 생성 전 중단됐음을 확인하고, positional argument 없이 입력하는 방식으로 수정했다. 설치 때 사용하는 실제 함수의 stdin 회귀와 검토 정책 compile을 검사한 뒤 소유자의 두 번째 설치가 성공했다. 일반 사용자 `check`는 커널 profile 목록 권한 때문에 EACCES다. 문서의 sudo check와 비밀 없는 실제 runtime proof를 구분한다.

## 다음 실제 검증의 선행 조건과 한계

승인된 순서는 설치 → 같은 NoNewPrivileges 조건의 보호 검사 → 별도 state/전용 repo의 R6다. 보호 검사는 실제 secret/account/thread를 쓰지 않는다. R6는 최대2개 Codex job/30분, job당300초이며 기존 API·dot/Muse·웹 GPT 요청은0이다. 실제 command 승인·원본 반영/owner 독립 검토는 구체 내용을 제시한 뒤 받는다. source는 `validation.txt` 하나이며 사용자 제품 저장소에는 쓰지 않는다.

설치된 CLI와 함께 있는 protocol source의 정적 조사 후 **실제0.166.0에서도 무호출 확인**했다. 임시 repo와 빈 전용 home(credential0)에서 `thread/start(ephemeral:false)`와 같은 프로세스 read는 성공했지만 rollout 파일은 없었고, 별도 프로세스 read/resume는 둘 다 `rpc_rejected`였다. 실제 model turn0이며 준비용 디렉터리는 정리했다. 현재 앱의 기존 thread 등록/재개 계약에 전달할 수 없다. 지원되지 않는 thread 조작이나 warm-up 모델 호출을 추가해2회 한도를 우회하지 않았다.

기존 readOnly 정책은 broad read다. 가짜 auth.json만 준비해 전용 외부 경계 안에서 실제 CLI의 built-in `:read-only` profile을 실행했으며 `LEGACY_AUTH_READABLE`을 관측했다. **실제 인증을 노출한 검사가 아니며 모델 호출0이다.** 보호 쓰기의 named profile은 auth deny를 갖지만 이를 legacy 읽기 정책에 자동 승계할 수 없다. 실제 readonly 모델 요청0을 유지하고 최소 읽기 범위 보완·세션 준비의 추가 계획/변경량을 먼저 보고한다.

## 보존·복귀

새 정책/도구는 운영 설정과 분리한다. 실제 보호 실패/추가 권한 요청·원문 gap·불명확한 실행은 차단/미확정으로 기록하고 재전송하지 않는다. 종료 시 실제 실행0을 대조하고 검증 권한 회수·temporary credential 제거, 원문/digest/receipt 보존을 확인한다. 기존 state·Chrome·계정·이력·API 정책은 그대로 둔다. 전용 파일이 패키지/검토본과 다르거나 실행이 남아 있으면 자동 제거하지 않는다. 운영 배포·R6-F 전체/원래 R8 gate는 실제 증거 전 완료로 표시하지 않는다.
