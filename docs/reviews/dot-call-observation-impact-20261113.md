# dot 교차검토 단계별 진단 — 영향·변경량 검토

상태: **APPROVED — 2026-11-13 사용자 ‘메타데이터 진단 계획 개정·개발 승인’**. 기준 main `e580cec8c38d02020ddabe125d3d8f5bffee84f7`(PR #65), 운영 제품 소스는 `5d5c824`와 동일하다. 11월13일 요청은11월10일 native 교차검토 timeout의 원인 조사·수정과 기존 완료5개 보존이다. 아래 선택형 진단의 계획 개정·개발·합성 검사가 승인됐으며, 운영 적용·새 모델 호출은 포함하지 않는다. [구현·검사 결과](../implementation/dot-cross-review-diagnosis-20261113.md)와 구분한다.

## 문제와 근거

- 실제 이벤트 전달/claim은22:28:45/22:29:35 KST에 성공했다. 마지막 MCP 전달 패킷은22:31:17이고22:33:42에300초 timeout이었다. 패킷57개/숫자 RPC id1 전달19개만 기록돼 있으며 메서드·페이지·성공/오류를 구분할 수 없다. 이를17페이지 읽기 완료로 판정하지 않는다.
- `DotMcpAdapter.call`의 get은 Store 읽기 전용이고, 거절된 submit·실패한 get은 durable event가 없다. `McpEndpoint.handle`은 오류를 반환하지만 단계별 운영 로그를 남기지 않는다. `mcp-stdio.mjs`도 전달 실패를 일반 오류로 바꿔 원래 HTTP/RPC 결과가 서버 기록에 남지 않는다.
- 보존 입력17페이지의 순수 분할/해석은 로컬 약85ms, 실제 handler를 가짜 권한/분리된 메모리 state로 호출한17페이지는 기존10개 mailbox를 포함해 약894ms였다. 이는 원문/응답 계약의 재현이며 실제 native 지연 원인이나 읽기 성공 증거는 아니다.
- 제출 크기 초과 시 응답 ID를 읽기 전에 거절해 무응답이 되는 별도 전달기 결함을 재현했다. 이 예외 응답 수정은 기존 전송 제한/오류 계약 안에서 진행하며, 이번 timeout의 원인으로 확정하지 않는다.

## 대안과 권장안

| 대안 | 판단 |
|---|---|
| 현재 로그와 실제 dot 실행 기록 대조만 유지 | 기존 기록을 가장 적게 바꾼다. 실제 dot 보고가 남아 있으면 우선 사용한다. 보고가 없으면 과거 단계 복원은 불가능하다. |
| DB에 page-read/submit-failed event 저장 | durable 조회가 쉬워지지만 get의 Store0 writes 계약을 바꾼다. 현재 최소안에서 선택하지 않는다. |
| 전체 요청/응답 payload 수집 | 대화/attemptToken 노출 위험과 큰 기록을 만든다. 기각. |
| **선택형 전달기 메타데이터 로그** | 승인·채택. 도구 응답/페이지/DB 계약을 유지하며 요청 도착·응답 반환·전송/프로토콜 오류를 구분한다. 원문/키/토큰은 기록하지 않는다. |

## 최소 계약·파일 범위

- `scripts/mcp-stdio.mjs`에 `WJ_MCP_TRACE=summary` 선택 기능을 둔다. 기본은 off이며 stdio의 프로토콜 stdout은 바꾸지 않는다. 기존 stderr를 통해 운영자가 관리하는 로그에만 쓴다.
- **신규** `scripts/mcp-call-trace.mjs`는 허용한 필드만 만드는 projection/기록 helper다. 도구 종류(metadata/page/claim/submit, 그 외 other), 요청 ID의 SHA256 참조, 안전한 정수 pageIndex/pageCount, 바이트 수, 시작/완료 시각·소요 시간, HTTP 상태·허용된 RPC 오류 분류만 사용한다. 원문·이메일·URL·grant/attemptToken·commandId·임의 오류 메시지·stack은 제외한다. 비정상 자료와 로그 오류가 실제 요청 결과를 바꾸지 않아야 한다.
- 응답 반환은 **로컬 전달기에서 응답을 구성했다는 관측**이며 native가 읽었다거나 추론을 마쳤다는 증거가 아니다. 전 페이지 반환 뒤 제출 없음은 외부 생성 단계의 미확인으로 남긴다.
- `tests/mcp-call-trace.test.mjs`(신규)와 기존 전달기 회귀 검사에서 정상/오류/누락/권한 거절/크기 초과·비밀 제외·stdout 불변·off 무기록·기록 실패 시 요청 보존을 확인한다.
- D4 운영 절차, 진단 구현 기록, SSOT에서 opt-in/관측 의미와 한계를 설명한다. UI·새 endpoint·MCP 입력 schema·SQL 이관은 없다.

**전체 예상: 7~8파일·220~380줄.** 전달기/helper 약70~110줄, fixture 약100~180줄, 문서/SSOT 약50~90줄이다. 현재 예외 응답 수정은 별도 실제 diff로 기록하며 이 제안 규모에 중복 합산하지 않는다.

구현 범위는 진단8파일이며, 첫 CI에서 발견된 기존 시각/중단 준비 경쟁을 고치는 테스트 fixture2파일이 추가됐다. 제품 기능·호스트·수락 범위 추가는 없다. 실제 diff와 검사 결과는 연결된 구현 기록 및 PR에서 확인한다.

| 단계 | 영향과 유지 계약 |

| R3 GUI | 화면 변경 없음. 진단 로그를 모델 대화나 공개 SSE에 노출하지 않는다. |
| R4/D3·D4 연결 | 전용 전달기의 선택형 stderr 진단만 추가한다. 도구/Events/권한/페이지 경계·기존 Muse 연결 유지. |
| R5 업무/R6 실행 | 업무 pickup·Codex 보호/승인/원본 반영 계약과 실제 호출0을 유지한다. |

현재+후속 변경량은 위7~8파일 범위로 예상한다. 운영 활성화는 별도 실제 적용 시 기존 private bridge env1줄을 잠시 설정하는 방식이며 호스트 서비스/보호 정책/네트워크 노출 변경은 없다. 그 활성화와 새 실계정 호출은 이번 개발 승인에 포함하지 않는다.

## 수락·롤백·승인 대상

1. 같은 fixture에서 stdout RPC 결과/원문 digest와 요청 전달 수가 off/on 모두 동일하고 로그에 합성 비밀/원문이0건임을 검사한다.
2. page0/중간/마지막·submit 거절·HTTP401/429·전송 timeout·크기 초과가 정해진 메타데이터로 구분돼야 한다. 고의 오류의 문자열을 그대로 로그에 내보내지 않는다.
3. `npm run check`와 관련 전달기 fixture를 수행한다. 구독/모델/실제 방 변경이 없는 합성 결과와 실계정 결과를 구분한다.
4. 원복은 선택 env 제거와 기존 전달기 사용이다. DB/과거 요청/원문/receipt는 쓰거나 삭제하지 않는다. 선택 기능 오류가 추가 재시도를 만들면 수락하지 않는다.

승인 대상은 **선택형 메타데이터 진단의 계획 개정·개발·모의 검사**다. 입력 축약/변경·300초 연장·페이지 상한 확대·새 모델 호출·과거 실패 자동 재시도·운영 적용은 포함하지 않는다. 과거 실패 원인을 새 로그가 소급해 증명한다고 표시하지 않는다.
